## 二、八个失败（按严重程度）

### 失败 1｜差点把"作业现场"当成"产品"发布

C4B 的目录里有：`_starter/`（基座原件）、`evidence/`（18 个取证文件）、`site/`、若干临时 HTML、`.skill` 包。
我最初的念头是"把这个目录传上 GitHub 就行了"。

**这个念头错得很典型**：`evidence/` 是**给我自己看的取证材料**——跑分记录、失败截图、"这里我曾经写错"的痕迹。
它对评审有用，对一个想用这个工具的路人**全是噪音**：clone 下来看到 18 个不知干什么的文件，然后关掉页面。

→ 仓库只留**使用者需要的**；取证材料压缩成 `docs/official-evidence.md` 里的一张依据表。

**规则：作品集不是档案柜。"我做过什么"和"你能用它做什么"是两份清单，混在一起会同时毁掉两边。**

### 失败 2｜README 的"示例"我凭印象写了一篇不存在的文章

初稿"输入示例"是《为什么你的公众号排版一粘贴就崩》，结构完整、语气自然——**但样例文件根本不是那篇**。
我是准备贴终端输出时顺手 `cat` 了一下样例文件才发现的。

AI 生成"示例"时模仿的是"示例段应该长什么样"，不是"这个仓库里到底有什么"。

**规则：示例必须复制粘贴自真实文件。任何"举例说明"的地方，先打开那个文件再说。**

### 失败 3｜徽章写 20/20，正文写 18/20，同一页两个数

两个数都是真的（满依赖 / 干净环境），错在并排放却不加区分——读者只会读到"这仓库自己都说不清"。

→ 徽章改成 `selftest-20 checks`（陈述检查项数，不陈述通过率）。

**规则：徽章是承诺，不是装饰。任何"通过率"类徽章，写之前先问"我这台机器现在跑得出这个数吗"。**

### 失败 4｜移植来的核验脚本"静默失效"——SKIP 被当成了通过

从 C4B 搬过来的 `verify_official_quotes.py` 三处路径写死，跑起来一堆 `⚠️ SKIP —— 文件不存在`。

**最危险的不是它坏了，而是坏了还返回 0**：SKIP 不计入失败，CI 会显示绿色——
一条"官方依据核验"的绿灯，实际一条都没验。

**规则：移植代码后第一件事不是"能不能跑"，而是"它到底跑了没有"。凡是能返回成功却什么都没做的分支（SKIP / 空循环 / 0 个用例），都要在输出里显式计数。**

### 失败 5｜10 条官方原文"全部消失"，其实是 gzip 没解压

修完路径再跑，10 条全部报"未在页面上找到"。第一反应是"微信改文档了"——这个结论很诱人，因为听起来不是我的问题。

多查一层：把抓回的内容打出来，是乱码。官方站返回 `Content-Encoding: gzip`，脚本 `decode("utf-8","ignore")`
把解压失败全吞了。补 `gzip.decompress` 后 **10/10 全部通过**（2026-11-03 实测）。

**规则：`decode(errors="ignore")` 和 `except: pass` 是同一类东西——把"失败"变成"看起来成功"。以及：结论如果刚好对你有利，先加倍怀疑。**

### 失败 6｜CONTRIBUTING 里写了"argparse choices 是硬编码的"——不是

写"加一套主题"的分步教程时凭印象写了"要记得改 `--theme` 可选值，因为 choices 是硬编码列表"，还加了句"这一步最容易漏"。
实际是 `choices=T.THEME_NAMES`，而 `THEME_NAMES = list(THEMES.keys())`——**加键就自动可用，没有第二处可改。**

照着做的人会去找一个不存在的列表，找不到就开始怀疑文档。

**规则：写"你必须记得改 X"之前，先 `grep` 一下 X 在哪。给别人的操作步骤最经不起凭印象写。**

### 失败 7｜ATTRIBUTION 里把正文写成 15px，实际 16px

写"这些 CSS 数值是我自己调的"时顺手写了"正文 15px / 行高 1.75 / 段间距 1.2em"，
实际是 **16px / 1.75 / 12px**。三个数字错两个。

讽刺的是：这一行本来是为了证明"我很熟悉自己的项目"——**恰恰是这种"表达所有权"的句子最容易掺假**，
因为它不是在陈述可查的事实，而是在陈述"这是我的"。

**规则：凡涉及具体数值的句子，写完立刻打开源文件对一遍。尤其是那些"用来证明我很懂"的句子。**

### 失败 8（未解决）｜没有 GitHub 凭据，不能替自己决策"要公开"

本机 `ssh -T git@github.com` 返回 `Permission denied (publickey)`，`gh` CLI 未安装。
我能把仓库准备到"一条命令就能推"，但**不能替自己决定要不要公开、用哪个账号公开**——这需要人确认。

处理：不伪造链接。`repo链接.md` 的 URL 是**预填 + 明确标注"推送后请核对"**，并附推送指南与一键脚本。

**规则：需要账号/权限的外部动作，交付"最后一步的完整操作"比交付"看起来完成的状态"更有用，也更诚实。**

## 三、做对的四件事

1. **先定"给谁看"，再定目录结构。** 一开始就问"clone 下来的人想干什么"（跑一次 / 改主题 / 报 bug），
   目录按这三种动作组织，而不是按我写代码的顺序组织。
2. **保留上游基线做对照。** starter 原版输出、C4B 的 20 项 selftest 记录都留着，"我改了什么"因此可量化，不是自述。
3. **把规则写成可执行检查。** `wechat_check.py`、`selftest.py`、`verify_official_quotes.py` 全部接进 CI——文档会过期，检查不会。
4. **两个环境的数字分开报。** 18/20 与 20/20 并列写并解释差异来源，比只写好看的那个更经得起复跑。

## 四、和 C4B 那次的区别（这次真的改了什么）

C4B 的 AAR 我写了"七个失败"，其中最扎心的是两条：**写了一条自己都查不到出处的规则**（"100 张"）、
**留档 20/20 却没写解释器导致复跑必然对不上**。

这次我把那两条教训变成了流程，而不是写进反省：

| C4B 的教训 | C5 落成了什么 |
|---|---|
| 数字必须绑机器 + 解释器 + 依赖状态 | README 的「质量保证」节把两种环境并排列，冒烟测试也补了 8/8 |
| 写进文档的数字必须当场给出处 | 规则表每条标 L1–L4；新增 `docs/official-evidence.md` 摊开原文与冲突 |
| 查不到出处就标"未找到" | 4 条规则明确标"未找到官方出处 + 实测"，没有伪装成官方条文 |
| 删掉的错误要有护栏 | "100 张"写进核验脚本做回归断言，重新出现即报错 |

**但仍然有新的同类错误出现**（失败 6、7 都是"凭印象写事实"）。这说明：
把教训写成流程能挡住"已知的坑"，挡不住"同一类错误换个地方发生"。
真正有效的是**把核对动作放在写完的下一秒**，而不是放在复盘时。

## 六、一条可迁移的结论

这次表面做的是"给一个技能建 GitHub 仓库"，实际训练的是：

**把"我知道它好用"翻译成"陌生人在 5 分钟内能验证它好用"。**

差别在这几处：

- "我测过 20 项" → "20 项在哪、怎么跑、什么环境跑出什么数、掉的是哪两项"
- "规则来自官方文档" → "哪一页、哪一句、什么时候核验过、核验脚本在哪、抓不到网时怎么表现"
- "很容易扩展" → "改哪个文件，第几步容易漏，漏了会报什么错"

每一条都是把**内部状态**转成**外部可验证的信号**。这和写代码不是一回事——
代码只要对机器成立；文档要对一个**不信任你的人**成立。
