## 一、开工前先定的一件事

C5 有七种项目类型可选（skill 包 / prompt 集 / 脚本 / Agent / 数据集 / 文档 / Web App 源码）。
我选 **「把 C4B 的 wechat-publisher 技能仓库化」**，理由是 CHALLENGE.md 里那句话——

> 你可以把 C5 理解为：**给你的 C4 技能一个"家"**。

这条路径有三个好处：① 代码是验证过的（20 项 selftest 在手）；② C4→C5→C6 是同一流水线，后面 C6 可以直接拿这个仓库去部署；
③ 它逼我面对一个真实的转化问题：**一个"我自己能用"的技能，和一个"陌生人能用"的项目，差在哪。**

事后看，这个判断是对的，但**差在哪这件事比我想的难**——见第四节。

## 三、6 次返工（本次真实发生，按发现顺序）

### 返工 1｜README 的"示例"是 AI 编的一篇不存在的文章

初稿"输入示例"写的是《为什么你的公众号排版一粘贴就崩》，结构完整、语气自然——但 `examples/sample_article.md`
根本不是那篇。**我准备贴终端输出时顺手 `cat` 了一下样例文件才发现。**

AI 写"示例"时模仿的是"一个 README 的示例段应该长什么样"，不是"这个仓库的文件里到底有什么"。

→ 把示例换成真实文件内容的真实节选。

### 返工 2｜徽章写 20/20，正文写 18/20，同一页两个数

两个数都是真的（满依赖 20/20、干净环境 18/20），但并排放在一页却不加区分，读者只会读到"这个仓库自己都说不清"。

→ 徽章改成 `selftest-20 checks`（陈述"有 20 项检查"，不陈述通过率），通过率交给正文分环境说明。

### 返工 3｜样例转换第一次跑出「图片未找到」

迁移文件时漏了 `examples/img.png`，转换告警 `[提醒] 图片未找到，已保留原路径`。
→ 补图重跑，README 贴的输出换成修复后的最后一次真实输出。

### 返工 4｜移植来的核验脚本"静默失效"——SKIP 被当成通过

`tests/verify_official_quotes.py` 从 C4B 的 `evidence/` 搬过来，三处路径写死：`卢怡然_C4B_文章源文件.md`（仓库里没有）、
`wechat-publisher/references/...`（多了一层）、输出文件名带中文。

**最危险的是它坏了还返回 0**：`SKIP` 不计入失败，CI 会显示绿色——一条"官方依据核验"的绿灯，实际一条都没验。
→ 路径改为相对仓库根解析，输出名改 ASCII。

### 返工 5｜10 条官方原文"全部消失"，其实是 gzip 没解压

修完路径再跑，10 条全部报"未在页面上找到"。第一反应是"微信改文档了"——这个结论很诱人，因为听起来不是我的问题。

多查一层：把抓回的内容打出来看，是乱码。官方文档站返回 `Content-Encoding: gzip`，
而脚本 `bytes.decode("utf-8", "ignore")` 把解压失败全吞了。
补 `gzip.decompress` 后 **10/10 全部复核通过**（2026-11-03 实测）。

### 返工 6｜CONTRIBUTING 里写了句"argparse choices 是硬编码的"——不是

写"加一套新主题"的分步教程时我凭印象写了"要记得改 `--theme` 的可选值，因为 choices 是硬编码列表"，还加了句"这一步最容易漏"。
实际是 `choices=T.THEME_NAMES`，而 `THEME_NAMES = list(THEMES.keys())`——**加键就自动可用，根本没有第二处可改。**

如果没查，照着做的人会去找一个不存在的列表，找不到就开始怀疑文档。
→ 改成正确的步骤（跑 `--list-themes` 验证即可）。

> 同类的还有第 7 处：ATTRIBUTION 里我把正文写成了"15px"，实际是 16px。**偏偏是这种"用来证明我很懂"的句子最容易掺假。**

## 四、这次真正难的地方：把"内部状态"翻译成"外部可验证的信号"

C4B 的交付物是给**评审**看的（有 evidence 留档、有 AAR），C5 的交付物是给**陌生人**看的。差别在这几处：

| C4B 的说法 | C5 必须变成 |
|---|---|
| "我测过 20 项" | 20 项在哪、怎么跑、什么环境跑出什么数、掉的是哪两项、为什么掉 |
| "规则来自官方文档" | 哪一页、哪一句、什么时候核验过、核验脚本在哪、抓不到网时怎么表现 |
| "很容易扩展" | 改哪个文件、第几步容易漏、漏了会报什么错 |
| "有 AI 参与" | 哪个环节 AI 写的、哪个环节我手写的、AI 写错过什么、我怎么发现的 |

这也是我把 `evidence/`（18 个取证文件）**不搬进仓库**的原因：那是"我做过的证据"，不是"你能用的东西"。
它被压缩成 `docs/official-evidence.md` 里的一张依据表——**作品集不是档案柜**。

## 五、手写 / 人工决定的部分（反向举证）

CHALLENGE.md 说"手动步骤的反向举证同样适用"，所以这里逐条说明：

| 内容 | 为什么不由 AI 定 |
|---|---|
| 18/20 与 20/20 必须分环境报 | 这是最容易被质疑的点，AI 倾向只写好看的那个数 |
| 否掉 `pyproject.toml` / pip 安装方案 | 与"零依赖 clone 即跑"的主承诺冲突，属产品定位取舍 |
| "查不到官方出处就标未找到" | 诚实边界，不是技术选择（4 条规则因此没有官方条文背书） |
| "SKIP 不是通过"的门槛口径 | 失败 4 的根因就是 SKIP 太便宜 |
| AAR 里保留 8 个失败（而不是 3 个） | 只写成功经验的复盘等于没复盘 |
| 是否推送、用哪个账号推 | 外部动作 + 需要凭据，AI 不得代替确认（本文写作时仍未推送） |

## 六、Prompt 演进（真实的三次收紧）

1. **第一轮（宽）**：「帮我把这个技能变成一个别人能用的 GitHub 项目」
   → 得到了一份"标准开源项目长什么样"的通用结构，正确但空——它没有利用"这个项目已经验证过 20 项"这个事实。

2. **第二轮（收窄到证据）**：「README 里的每个数字都要能对应到一次真实执行；没有的依据就写'未找到'」
   → 文档立刻变得具体，`docs/official-evidence.md` 这种"把依据摊开"的文档就是这么来的。

3. **第三轮（收窄到反证）**：「找出这份文档里有没有你编的东西」
   → 一次抓出 4 处：假想示例文章、20/20 徽章、15px 的 CSS 数值、硬编码的 argparse choices。

**结论：让 AI"写一份好文档"，不如让 AI"证明这份文档没有假话"。前者产出漂亮，后者产出可信。**
