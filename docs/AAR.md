# AAR：把一个"能用的技能"变成"别人能用的仓库"

> AAR = After Action Review。复盘的价值不在"我很努力"，而在**下一次少踩同一个坑**。
> 所以这份文件里，失败占的篇幅比成功多。

---

## 一、结果对照

## 二、七个失败（按严重程度排序）

### 失败 1：差点把"作业现场"当成"产品"发布

C4B 的目录里有什么？`_starter/`（基座原件）、`evidence/`（18 个留档文件）、`site/`、若干临时 HTML、`.skill` 包。
我最初的念头是"把这个目录传到 GitHub 就行了"。

**这个念头是错的，而且错得很典型**：`evidence/` 是**给我自己看的取证材料**，里面有跑分记录、失败截图、
"这里我曾经写错"的痕迹。它对评审有用，对一个想用这个工具的路人**全是噪音**——他 clone 下来会看到
18 个不知道干什么的文件，然后关掉页面。

处理：仓库只保留**使用者需要的东西**（源码 / 参考文档 / 示例 / 测试 / 贡献指南）；
取证材料压缩成 `docs/official-evidence.md` 里的一张依据表，原始留档留在 C4B 交付包里，不搬进来。

→ **规则：作品集不是档案柜。"我做过什么"和"你能用它做什么"是两份不同的清单，混在一起会同时毁掉两边。**

### 失败 2：README 的"示例"我先凭印象写了一篇不存在的文章

初稿里"输入示例"是一篇叫《为什么你的公众号排版一粘贴就崩》的文章，结构完整、语气自然——
**但 `examples/sample_article.md` 根本不是那篇**。我是准备贴终端输出时顺手 `cat` 了一下样例文件才发现的。

AI 生成"示例"时极容易产出"看起来该是这样"的内容。它模仿的是"一个 README 的示例段应该长什么样"，
而不是"这个仓库的样例文件里到底写了什么"。

→ **规则：示例必须复制粘贴自真实文件。任何"举例说明"的地方，先打开那个文件再说。**

### 失败 3：徽章写 20/20，正文写 18/20，同一页两个数

初稿顶部徽章是 `selftest-20/20`（好看），正文"质量保证"节诚实写了"干净机器 18/20"。评审第一眼就会抓这个。

有意思的是：**两个数都是真的**，20/20 是满依赖环境、18/20 是干净环境。错的是我把它们放在同一页
却不加区分——读者只会读到"这个仓库自己都说不清"。

处理：徽章改成 `selftest-20 checks`（陈述"有 20 项检查"，不陈述通过率），通过率交给正文分环境说明。

→ **规则：徽章是承诺，不是装饰。任何"通过率/百分比"类徽章，写之前先问"我这台机器现在跑得出这个数吗"。**

### 失败 4：移植来的核验脚本"静默失效"——SKIP 被当成了通过

`tests/verify_official_quotes.py` 是从 C4B 的 `evidence/` 搬过来的。搬完直接跑，输出里有一堆 `SKIP`：

```text
⚠️ SKIP —— 文件不存在
```

原因：脚本里三处路径是写死的——`卢怡然_C4B_文章源文件.md`（仓库里没有这个文件）、
`wechat-publisher/references/...`（仓库根就是 `wechat-publisher/`，多了一层）、
输出文件名带中文（CI 上容易出编码问题）。

**最危险的地方不是它坏了，而是它坏了还返回 0**：`SKIP` 不计入失败，脚本以退出码 0 结束。
如果我没看输出，CI 会显示绿色——一条"官方依据核验"的绿灯，实际上一条都没验。

处理：三处路径改为相对仓库根解析，输出文件名改 ASCII；并在 `AI_LOG.md` 里写明"SKIP 不是通过"。

→ **规则：移植代码后第一件事不是"能不能跑"，而是"它到底跑了没有"。凡是能返回成功却什么都没做的分支（SKIP / 空循环 / 0 个用例），都要在输出里显式计数。**

### 失败 5：10 条官方原文"全部消失"——其实是 gzip 解压没做

修完路径再跑，10 条官方原文**全部报"未在页面上找到"**。第一反应是"微信改文档了"——这个结论很诱人，
因为它听起来像"不是我的问题"。

再查一层：把抓回来的内容打出来看一眼，是乱码。原因是官方文档站返回 `Content-Encoding: gzip`，
而脚本直接 `bytes.decode("utf-8", "ignore")`，`ignore` 把解压失败全吞了，得到 5504 个字符的垃圾。

补上 `gzip.decompress` 后，**10/10 全部复核通过**（2026-11-03 实测）。

→ **规则：`decode(errors="ignore")` 和 `except: pass` 是同一类东西——它们把"失败"变成"看起来成功"。
以及：结论如果刚好对你有利（"是别人改了，不是我错了"），先加倍怀疑。**

### 失败 6：CONTRIBUTING 里写了句"argparse choices 是硬编码的"——不是

写"加一套新主题"的分步示例时，我凭印象写了第 2 步："要记得改 `convert_to_wechat.py` 里的 `--theme` 可选值，
因为 `argparse` 的 `choices` 是硬编码列表"。写得很像那么回事，还配了句"这一步最容易漏"。

实际一查：`p.add_argument("--theme", choices=T.THEME_NAMES, ...)`，而 `THEME_NAMES = list(THEMES.keys())`。
**加键就自动可用，根本不需要改第二处。**

如果没查，这个 PR 会带来一个真实的坏后果：贡献者照着做，去找一个不存在的"硬编码列表"，
找不到就开始怀疑文档，最后可能放弃。

→ **规则：写"你必须记得改 X"之前，先 `grep` 一下 X 在哪。给别人的操作步骤是最经不起凭印象写的东西。**

### 失败 7：ATTRIBUTION 里把正文写成了 15px，实际是 16px

写"这些 CSS 数值是我自己调的，不是抄的"时，我顺手写了"正文 15px / 行高 1.75 / 段间距 1.2em"。
实际 `references/wechat_styles.md` 写的是 **16px / 1.75 / 段间距 12px**。三个数字错两个。

讽刺的是：这一行本来是为了证明"我对自己项目很熟"。**恰恰是这种"表达所有权"的句子最容易掺假**——
因为它不是在陈述一个可查的事实，而是在陈述"这是我的"。

→ **规则：凡涉及具体数值的句子，写完立刻打开源文件对一遍。尤其是那些"用来证明我很懂"的句子。**

### 失败 8（未解决）：没有 GitHub 凭据，不能替用户推仓库

本机 `ssh -T git@github.com` 返回 `Permission denied (publickey)`，`gh` CLI 未安装。
也就是说：**我能把仓库准备到"一条命令就能推"的程度，但不能替他决定要不要公开、用哪个账号公开。**

处理：不伪造链接。交付包里 `卢怡然_C5_repo链接.md` 的 URL 是**预填 + 明确标注"推送后请核对"**，
并附 `推送指南.md` 与 `push_to_github.sh`。

→ **规则：需要账号/权限的外部动作，交付"最后一步的完整操作"比交付"看起来完成的状态"更有用，也更诚实。**

## 三、做对的四件事

1. **先定"给谁看"，再定目录结构。** 一开始就问"clone 下来的人想干什么"（跑一次、改主题、报 bug），
   目录按这三种动作组织，而不是按"我写代码的顺序"组织。
2. **保留上游基线做对照。** starter 的原版输出、C4B 的 20 项 selftest 记录都留着，
   "我改了什么"因此是可量化的，不是自述。
3. **把规则写成可执行检查。** 这次仓库化把 `wechat_check.py`、`selftest.py`、`verify_official_quotes.py`
   接进了 CI——文档会过期，检查不会。
4. **两个环境的数字分开报。** 18/20 与 20/20 并列写、并解释差异来源，比只写好看的那个更经得起复跑。

## 四、改进方案（下一步真的会做的）

| 优先级 | 事项 | 为什么 |
|---|---|---|
| P0 | 推送仓库 → 回填真实 URL → 看 Actions 是否真的绿 | 只有这一步做完，"可复现性"才从声明变成事实 |
| P0 | 有公众号账号后，做一次真实粘贴实测并截图留档 | 坑 1/2/3/6 目前只有历史实测，无本次留档（`docs/official-evidence.md` 已如实标注） |
| P1 | 把双引擎等价测试扩到嵌套表格、脚注、定义列表 | 目前等价性只覆盖 20 项里的常用语法 |
| P1 | 加"上一次转换 vs 这一次"的回归对比脚本 | 改代码后能快速确认没有退化，比人眼看 diff 可靠 |
| P2 | 给 `SKIP` 加"少于 N 项即视为失败"的门槛 | 失败 4 的根因是 SKIP 太便宜 |
| P2 | 公式渲染换完整 LaTeX 引擎（支持宏包） | mathtext 是子集，复杂公式渲染不了；当前降级告警可兜底 |
| P3 | 英文 README | 目前只有中文；如果想让非中文用户用，这是必需项 |

## 五、一条可迁移的结论

这次表面做的是"给一个技能建 GitHub 仓库"，实际训练的是：

**把"我知道它好用"翻译成"陌生人在 5 分钟内能验证它好用"。**

差别在这几处：

- "我测过 20 项" → "20 项在哪、怎么跑、什么环境跑出什么数"
- "规则来自官方文档" → "哪一页、哪一句、什么时候核验过、核验脚本在哪"
- "很容易扩展" → "加一个主题改哪个文件，第几步会漏，漏了会报什么错"

每一条都是把**内部状态**转成**外部可验证的信号**。这件事和写代码不是一回事——
代码只要对机器成立，文档要对一个不信任你的人成立。
